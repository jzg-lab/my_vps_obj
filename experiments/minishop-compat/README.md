# Minishop 多服务兼容性离线检查

日期：2026-10-22（北京时间）。本实验只验证选定源码函数的行为，不是可部署的插件或产品实现。

## 检查范围

源码目标：Minishop `v3.8.2`，提交 `04b0ca5e210a33209bbf15485003865ee29304bc`。

直接从源码 AST 加载以下未修改的函数体，不导入整个应用或加载它的环境配置：

- `get_panel_user_uuids_for_user`：实际执行 SQLAlchemy 查询。
- `admin_user_ban_route`：执行身份枚举和封禁调用逻辑。
- `admin_user_delete_route` 及其缺失身份检查 helper：执行外部身份删除调用逻辑。

数据库为内存 SQLite，只有测试用核心订阅表和扩展服务表。面板 API、认证、缓存和本地账号删除动作均为替身；所有账号、连接身份都是虚构数据。测试不访问任何服务器。

## 运行

需要 Python 3.12。依赖只安装到本目录 `.venv`，不修改上游项目。

```sh
python3.12 -m venv experiments/minishop-compat/.venv
experiments/minishop-compat/.venv/bin/python -m pip install -r experiments/minishop-compat/requirements.txt
MINISHOP_SOURCE='/absolute/path/to/remnawave-minishop' experiments/minishop-compat/.venv/bin/python experiments/minishop-compat/test_account_lifecycle.py
```

命令从本项目根目录执行。`MINISHOP_SOURCE` 必须指向可信的本地源码；加载的是其中的 Python 函数。源码升级后，结果需要重新评估，不能沿用本次结论。

## 本次结果

运行环境：Python 3.12.14、SQLAlchemy 2.0.54。共运行 7 个检查，均与预期的**现有行为**一致，其中 3 个为正常路径对照、4 个复现扩展兼容性缺口。

| 场景 | 实际观察 |
| --- | --- |
| 核心表中保存同一账号的两份连接身份 | 封禁调用覆盖两份身份，不影响另一测试账号。 |
| 核心表中保存两份身份后删除账号 | 删除路由先调用面板删除两份身份，再调用本地账号删除。 |
| 面板拒绝封禁 | 路由返回失败，不提交本地封禁状态。 |
| 扩展表持有独立身份 | 原身份枚举函数不读取该表。 |
| 账号只有扩展身份 | 封禁路由返回成功并提交本地封禁状态，但没有发出面板停用调用。 |
| 账号同时有核心和扩展身份 | 只向核心身份发出停用调用。 |
| 删除只有扩展身份的账号 | 删除路由返回成功并调用本地删除动作，但没有发出对应面板删除调用。 |

`test_gap_*` 的通过表示成功复现遗漏，**不表示多服务方案通过验收**。本实验不能证明真实连接仍然可用，只能证明这些路由没有向扩展身份发出相应管理调用。

本实验没有验证完整宿主启动、插件安装、账号权限校验、实际删除级联、并发事务、同步任务、节点计量、订阅更新或实际网络停用；SQLite 结果也不能替代 PostgreSQL 的事务验证。

## 对方案的影响

“独立扩展表 + 直接沿用现有封禁／删除”不足以满足账号生命周期要求。下一步需要明确统一的生命周期接入点，覆盖管理后台及其他调用入口；不能只隐藏原有按钮，或把新服务插回核心订阅表来掩盖问题。

尚未证明纯官方扩展可以完成这种接入。若需要增加核心接口，应先列清修改范围、升级维护成本和故障处理，再决定是否采用局部二开。
