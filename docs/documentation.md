# 文档维护规范

本文规定文档的分工、分类和维护方式。代码质量门禁仍以仓库根目录 `CONTRIBUTING.md` 为唯一来源。

**交付物是仓库内的 Markdown 文档，供开发者和 agent 直接阅读。** 从根 `AGENTS.md` 进入[接手指南](handoff.md)和[分类目录](index.md)即可使用，不需要启动网页或预览服务器。整理文档不包含设计、发布文档网站；此类工作须另有明确任务。

## 1. 每种信息只维护一处

| 信息 | 权威文件 | 其他页面怎么引用 |
| --- | --- | --- |
| 产品边界、已确认和待定业务规则 | [需求基线](requirements.md) | 摘要加链接，不重复维护决策清单。 |
| 管理台流程、指标、工作包和验收规格 | [统一管理台实施指南](admin-console-guide.md) | 引用 UC／F／M／UA 编号。 |
| 全产品体验与服务生命周期 | [产品设计](product-design.md) | 管理台细节继续引用指南。 |
| 当前进度、实现和验收证据 | [实施计划第 14 节](implementation-plan.md#14-统一管理台执行追踪2026-10-24) | 不在首页、README 和技术参考复制测试数量或待办状态。 |
| 独立生产节点接入记录 | [实施计划第 15 节](implementation-plan.md#existing-node-onboarding-20261024) | 保留原环境、时间和授权范围，不合并成本地验收结论。 |
| 环境入口、路径与运维资料 | [项目环境记录](development/project-local.md) | 不复制密码、令牌、私钥或真实订阅。 |
| 工程约定和强制检查 | 根目录 `CONTRIBUTING.md` | `AGENTS.md` 和 `CLAUDE.md` 只负责指路与项目约束。 |
| 发布历史 | 根目录 `CHANGELOG.md` | 文档站由生成器发布，不建立第二份发布记录。 |

代码或现场证据与文档冲突时，核对原因并修正文档；如果冲突涉及尚未决定的业务规则，先取得用户决定。不能为了让文档“看起来一致”而改写验收结果或降低需求。

## 2. 分类

- **项目接手与规格**：入口、需求、指南、产品设计、架构决策和实施计划。
- **日常使用**：客户与管理员的操作手册、登录、客户端、客服和通知。
- **开发与运维**：隔离环境、启动、配置、备份、诊断、安全及维护。
- **技术参考**：模型、计量、交付、API、事件、兼容性及插件契约。
- **上游兼容与扩展**：原单订阅、支付、礼品、余额、营销、主题及其他机器人迁移。明确适用模式，保留仍有用的能力。
- **历史归档**：已结束阶段、被替代评估和原始交接证据。只用于追溯，不作为当前待办。

分类由仓库内的文档目录表达。已有路径仍有效时不为改名批量搬文件；这样能保留外部链接、代码引用和旧书签。

## 3. 一篇文档应该怎样写

开头说明读者、目的和适用范围。操作手册写任务、前置条件、步骤、结果和失败处理；技术参考写对象、契约、来源及边界。避免把讨论过程、执行者名字和不断累加的检查点塞进正文。

- 使用统一术语：账号／客户、套餐模板、独立服务、连接身份、节点、线路（Host）、节点组、专用出口。
- 区分已确认规则、设计约束、当前实现和实测结论。不能用“计划支持”代替已实现功能，也不能把“已实现”直接写成“已上线”。
- 日期写绝对日期，时间窗口注明时区。服务月度周期与节点图表时间窗口分别描述。
- 命令注明目标环境和前置条件；公开上游镜像、通用开发 seed、项目开发和生产操作不能混用。
- 对仍有效的旧链接保留锚点；不保留会误导接手者的过期结论作为现行说明。
- 未采集、未知、失败、部分数据和真实零值分开表述；测试跳过不能计为通过。
- 新功能文档随实现一起更新；没有核实的外部软件能力、版本和平台支持不写成保证。

## 4. 源文件与生成文件

| 内容 | 编辑位置 | 更新方式 |
| --- | --- | --- |
| 普通文档 | `docs/**/*.md` 与根 README／规则文件 | 修改源文档。 |
| 文档站 Markdown 副本 | `docs-site/src/content/docs/` | 运行 `npm run sync:docs`，不手改。 |
| 贡献指南与智能体入口 | 根 `CONTRIBUTING.md`、`AGENTS.md` | 直接阅读根文件，不额外生成站内副本。 |
| 现有文档工具索引 | `docs-site/astro.config.mjs` | 仅按既有检查要求登记新增文档，不据此扩大网页改造范围。 |
| HTTP API 规范 | 后端路由及类型化契约 | 用贡献指南指定生成器更新 OpenAPI 和前端类型。 |
| 事件、Remnawave 兼容目录 | 事件模型／面板能力声明 | 用各自生成器更新，禁止手改生成正文。 |

`docs/architecture-assessment.md` 保存已采纳架构决策摘要；初始源码调查保存在归档中。历史只追加勘误或补充来源，不静默修改当时的失败和未验收结果。

`docs-site/` 是仓库原有的文档与演示工具，不是本次文档整理的交付入口。既有生成器会读取 `docs/`，因此调整源文档时仍须保持其索引和链接兼容。生成或检查不等于发布；仓库文档中保留的上游站点地址也不代表本项目文档已经上线。

## 5. 文档交付检查

按贡献指南第 1 节选择检查：至少检查差异格式、内部路径与锚点，以及根入口到各分类的阅读路径。被现有文档工具读取的变更执行 `npm run check:docs` 和 `npm run build:docs`；这些是兼容性检查，不要求交付网页预览。实际修改网页交互时再执行规定的浏览器回归。

修改文档同步器时还须运行 `npm --prefix docs-site run test:docs`，检查仓库文件引用、旧锚点和 OpenAPI 链接兼容。此测试会重新生成副本，不与文档构建同时运行。

链接存在只证明能到达，不证明内容正确。还必须对照代码和实施证据检查模式、状态、业务规则及操作命令。对本次未覆盖的外部服务、生产环境或客户端平台如实说明。
