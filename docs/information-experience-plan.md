# 我的 VPN｜信息展示与运营闭环实施方案

版本：v1.0。日期：2026-10-24（北京时间）。

面向后续设计、开发、运营与验收人员。本文把信息展示研究转成可执行方案：**每个重要判断有证据，每个异常有下一步，每次处理有结果可核对。** 用户已认可方向并要求形成实施文档；这不等于新增经营规则已确定，也不代表产品改动已经实现。

本文是[统一管理台指南](admin-console-guide.md)的专题实施补充，不另建业务规则或 UC 工作包编号。业务边界以[需求基线](requirements.md)为准，页面职责参照[产品设计](product-design.md)。实际进度、证据和调整记录只维护在[实施计划的信息深化条目](implementation-plan.md#information-experience-tracking)；质量门禁仍以 [CONTRIBUTING.md](../CONTRIBUTING.md) 为准。

> **实践中发现问题，可以随时调整方案。** 本文是可检验、可修订的实施依据，不是必须机械执行的固定答案。可以依据源码、实测和真实任务反馈改变方法、措辞、顺序与任务拆分，并记录理由及新的验证办法。涉及业务规则、额外成本、采集或实施范围变化时，先取得明确决定；不得靠删除失败证据、降低验收条件或把未知改成正常来完成计划。调整流程见第 7 节。

## 1. 决策原则与范围

按照“使用者的问题 → 需要作出的判断 → 支持判断的事实 → 数据可信度 → 下一步动作 → 处理结果”组织工作。先确定信息能够改变什么判断，再决定是否展示、如何展示。

需要纠正的思维偏差：

- 有字段不等于有可靠事实；接口返回、离线测试、本地实读、真实代理测试与生产运行是不同证据。
- 权益有效、配置交付、管理连接正常与用户实际可用是不同层次，不压成一个“正常”。
- 未知是正常的信息状态；没有记录、没有新样本或读取失败，不能自动转成零。
- 技术交付与经营记录分别核对；开通不是收款，余额退款不是现金退回，现金净额不是利润。
- 按减少误判和支持处理验收，不以页面数、图表数或字段数评价完成度。

默认新增业务页面 0、新增图表 0、新增监控基础设施 0。复用现有“我的套餐”、服务详情、管理概览、客户、节点和操作记录。单值用数字，比较用表格／手机卡片；趋势图必须有真实历史、明确判断目的及后续动作。已有单份额度条仅比较该份用量与额度；条形可封顶，实际用量及超额数字不得截断。

不引入在线支付、自有 App、新监控平台、客户访问内容采集、全站视觉重做、自动故障切换、自动通知或新的服务质量承诺。经营事实先复用已有受控凭据或表格，不默认建设账务系统。文档、本地开发和研究不授权访问、探测或改动现用生产节点。

## 2. 两类使用者的最小信息

| 使用者与现有位置 | 最小信息 | 支持的判断及下一步 |
| --- | --- | --- |
| 用户：我的套餐 | 每份名称与可区分标识、业务状态、独立额度、已确认用量、剩余量、到期 | 找到正确服务，知道哪份耗尽／到期／暂停，不借用另一份额度。 |
| 用户：同份服务的时间说明 | 总包／月度、周期边界、重置条件、用量确认时间、未知或旧数据原因 | 区分重置与到期；无有效样本时不把初始零和配置额度称作已确认余额。 |
| 用户：详情与异常 | 交付结果、资源就绪情况、连接／更新订阅入口、已知原因及一项下一步 | 正确导入该服务；必要时提供服务标识、客户端版本、发生时间和脱敏错误，不提交完整订阅或访问历史。 |
| 管理员：概览 | 待核对／失败操作、对象、原因、等待时间、最近尝试与成功、来源状态 | 决定先处理什么，进入同口径明细；正常排队与故障分开。 |
| 管理员：客户与服务 | 全部独立服务、业务／执行／观测三类状态、用量与周期、订单及资源关系 | 定位哪份受限及处理动作；账号级与服务级操作的影响明确。 |
| 管理员：节点 | 管理连接、来源及时间、授权关系、潜在影响服务和去重账号；详情再看资源、流量 | 先判断管理面，再排查代理路径；授权关联不能称为正在连接或已经受影响。 |
| 管理员：经营与历史 | 开通／续期记录及原条款金额；收退款证据和核实状态在规则确认后补入现有区域 | 区分操作与实际收付；未核实不解释为欠款、零收入或已付款。 |

复用现有实体、工具栏、表格、状态和对话框组件，按贡献指南检查两个实际消费者。普通用户不接收内部堆栈和基础设施细节。当前缺少可靠来源的“你已连接”“你的网速／延迟／丢包”不填推测值。

## 3. 先落实指标合同

每个候选指标在实现前确定：使用者问题、统计对象与范围、原始来源／字段及版本、公式和去重键、单位、业务窗口及边界／时区、源采样或发生时间、读取及最后成功时间、完整性／错误原因、展示与动作、证据层级和未验证场景。尽量复用已有字段，不为统一外观新建状态机。

候选分四类：已有可靠数据可限定展示；原始数据已有但需最小聚合或补证；事实缺失需新增登记／采集；价值不足暂不展示。分类不代表上线状态。

| 对象 | 必须保留的口径 | 原始核查入口 |
| --- | --- | --- |
| 服务用量 | 剩余 `max(Q-U,0)`、超额 `max(U-Q,0)`；逐份、有有效样本才称确认；累计快照不重复相加。核对上游倍率与过滤阈值。 | `user_services`、`service_connections`、Panel 身份累计和精确载荷账。 |
| 服务周期 | Asia/Shanghai 原开通日锚点，月底取当月末；重试固定切点。到期不晚于下一边界时不暗示继续发额度。 | `service_usage_periods`、周期服务与月度切点。 |
| 客户／服务／身份 | 账号、现存账号服务、归档服务分开；客户按账号去重；身份、设备、连接不能互换。 | 业务模型及真实 summary／services DAL。 |
| 最近流量采集身份数 | 固定 Panel 的 `usersOnline` 不能直接称在线客户或连接数；过滤、缓存和采集失败可能产生零，缺有效性证据不作核心 KPI。 | Panel 3.4.5 采集处理器、系统缓存、本项目 Node 指标适配器。 |
| 管理连接／代理路径 | 管理连接只说明管理面；真实请求结果需位置、目标、协议、时段与样本范围。 | 节点清单、分层状态、真实客户端与受控目标。 |
| 内存／load／网卡 | 明确 Node 运行环境；load 不是 CPU%；默认网卡收发不是单用户网速或最大吞吐；读取时间不替代采样时间。 | Node 3.4.2 系统和默认网卡原始实现。 |
| Node 窗口流量 | 稳定 UUID 与完整库存合并，UTC 首尾包含日窗口；缺节点不补零；不是服务账或供应商账单。缺日补零不证明连续采集。 | Panel 节点历史 API／SQL、`admin_console_nodes_traffic.py`。 |
| 异常待办 | 复用 `needs_attention`，订单／执行去重；失败年龄与排队年龄分开；异常维度可能重叠，历史 unknown 不自动成为待办。 | 全局服务、账号及资源操作查询。 |
| 操作金额 | 开通取 `snapshot.terms`，续期取 `snapshot.change`；按订单去重、币种分组，不回填当前标价或推导已收款。 | `service_orders`、开通和续期 DAL。 |
| 实收／退款／成本 | 凭据原币金额和实际发生时间可追溯；内部余额与现金分开；收入确认、成本归属和分摊待决定。 | 原收退款凭据、支付／余额记录、供应商成本凭据。 |

源码定位见第 8 节，执行前重核当前版本与调用。例：服务“有采样的当前周期用量之和”不能称全站本月流量，最大最近成功时间不能证明全部对象健康，出口占用和待回收可能重叠。

经营来源还须防止两类误读：旧支付汇总直接求和 Float 金额、使用操作创建时间且不按币种拆分，不能直接作为本产品已核实实收或收入；空日补零也不证明线下收款记录完整。仓库已有兼容渠道退款记录和广告成本字段，因此不能笼统称为“没有退款／成本模型”，但这些局部字段不证明一期收退款、节点费用或全部成本已覆盖。独立服务订单与支付之间没有直接外键，不能按账号、相近时间或金额自行认定匹配。

| 数据状态 | 必须表达的事实 |
| --- | --- |
| 已知零 | 明确范围内有有效观测证明为零，带时间。 |
| 未知 | 证据不足及原因，不推断正常或故障。 |
| 未采集／不支持 | 尚无来源或能力，不能伪造历史。 |
| 过期 | 旧值保留原时间并邻近标注，刷新时间不覆盖源时间。 |
| 失败 | 本次失败与上次有效值分开；无有效旧值则未知。 |
| 部分 | 覆盖和缺失范围明确；覆盖本身未知时如实说明。 |

数据变旧不自动改变权益或断流；缓存 TTL 不充当网络 SLA；旧正值不维持“当前正常”。这些是展示语义，不新增一套业务状态机。

## 4. 分批实施与进入条件

以下批次是本专题拆分，不重开已完成的 UC 工作包。建议第一批优先，第二批的夹具同步准备；第三批业务确认可独立进行，不阻塞前两批；第四批随各批验证，最终汇总。状态只在实施计划维护。

### 第一批：可信展示与异常入口

**目标：** 消除最容易误导的标签、时间和汇总。

- 在既有用户卡片／详情区分用量、周期、到期、数据时效及连接验证；没有确认样本不显示确认余额。
- 管理概览突出可处理事项，数字进入同范围明细；分页长度不代替总数，异常重叠不假加成唯一故障数。
- 拆开管理连接、代理观测与资源值；不把身份数称在线客户，不制造 CPU 百分比、用户网速或伪历史。
- 补中／英／俄文和辅助技术状态文本；沿用已有契约，确实无法表达时才补最小字段并运行契约生成器。

**交付及退出条件：** 指标合同、受影响消费者、最小修改与对应第 5 节证据。源码、模拟、真实值分别登记，不以截图或接口有值代替验收。

**映射：** F01～F04；UC-01／02／03／05／09；UA-03～08／13／18／19。只声明实际触及和验证的行为。

### 第二批：关键反例与证据闭合

**目标：** 查明结论能覆盖哪些版本、路径和故障条件。

- 先只读 SQL／API／页面对账，再复用离线测试；只有真实路径才能回答的问题才使用隔离服务、客户端和受控目标。
- 核对倍率、过滤阈值和 reset 语义；跨节点／周期／重试不遗漏或重复计量。
- 保留默认 Node 同源误断失败基线；r3 只在已测版本／协议／环境内下结论，不通过展示绿灯替代执行验证。
- 覆盖管理通而代理失败、旧值保留、上游假零、历史缺口和采样时间缺失。发现历史说明超出报告范围时追加勘误，保留原报告。

**交付及退出条件：** 可复现命令、脱敏响应／载荷账、断言、失败／通过报告、清理和未覆盖范围。不能解决的问题说明影响，受影响能力保留未知或限定，不为了整批通过伪造结论。

**映射：** F02／03／04／06；UC-02／03／04／05／09；UA-04～08／10～13／18；计量和周期沿用需求 A05／A15～17／A20／A24。

### 第三批：最小经营事实与核对规则

**进入条件：** 先取得第 6 节经营决定；未确认前只解释记录范围和未核实，不推断欠款、零收入或已付款。

盘点现有凭据／受控表格，以少量脱敏样例验证凭据能否对应订单和服务。最小记录包括唯一凭据引用、收款／退款类型、原币金额、实际发生时间、核实人及时间、服务／订单关联和分配金额、退款原收款、更正／撤销关系。允许什么分配方式由业务决定。

同币种逐笔去重，内部余额抵扣不重复计现金；现金退款、余额退款与撤销权益分开。部分凭据只能说明已登记部分；记录覆盖充分时才计算该范围的已核实收款净额。缺失成本不填零，政策未确认不称收入或利润。

**交付及退出条件：** 业务决定、凭据样例、对账规则及差异；优先沿用已有记录和页面，验证确需持久关联后才提出最小模型变更。不预建账务平台。若触及余额退款，继续遵守 `TODO(balance-gift-refund)` 及其退款回归约束。

**映射：** 开通／续期操作记录属 F01／F04、UC-04／05。实际收退款、收入确认和成本分摊单列新增待确认经营规则，不强塞旧 UA 编号。

### 第四批：真实任务与交付验收

**目标：** 证明目标使用者能够理解和正确行动。

首轮建议 3 位一期目标用户及实际管理员；管理员只有 1 人即如实报告。普通用户独立找出哪份能用、解释余额时间／重置并完成该份导入或求助；管理员定位异常、解释潜在影响、识别收款未核实并找到下一步。使用合成／脱敏记录，不预先讲答案。

记录完成结果、关键误解、求助次数和耗时。出现额度互借、旧值实时、管理在线等于可用、授权人数等于连接数、开通等于收款的误判，修正信息后复测。人数是可调整的形成性研究建议，不是统计认证。真实任务与技术测试不能互相替代。

复用桌面／手机回归，检查窄屏、键盘、读屏、打开的菜单和对话框。按贡献指南完成相关门禁，分开登记实现、本地验收、真实环境验收与生产发布。

**交付及退出条件：** 任务记录、问题与修正、复测、可访问性和技术检查。待补场景及发布边界明确，不以主观“更专业”结项。

**映射：** F01～F05；UC-01／03／05／09；UA-19，权限继续满足 UA-02／20；经营理解任务单列。

## 5. 验收场景、方法与依据

### 必须覆盖的反例

| 场景 | 可观察的通过条件 | 证据及原验收关系 |
| --- | --- | --- |
| 同账号 A 耗尽或到期、B 有效 | A 与 B 逐份解释，B 权益／用量／旧长流不变；A 旧配置按原规则拒绝。展示与实际执行分别判。 | 状态样例＋隔离客户端；UA-03／10／12、A03／A05。 |
| 管理连接正常但代理失败 | 管理状态保持准确，实际失败或未验证明确，不显示整体正常，不把所有授权账号判为实际受影响。 | 分层故障夹具和受控目标；UA-13／18。 |
| 来源失败而页面留旧值 | 原时间、失败和年龄可见；无旧值则未知；恢复成功才更新。system 有值、身份统计失败写零也不判无人在线。 | 缓存／解析断言＋页面；UA-07。 |
| 跨节点、重复累计、多表关联 | 相同累计不重复扣，各对象按稳定标识去重；未知映射单列。 | 载荷账、SQL／API／明细；UA-04～06、A05／A16。 |
| 月末与跨周期响应丢失 | 31 日经 2 月回到 3 月原锚点；重试不移动切点或重复发额度；待确认不提前清零。 | 周期账和隔离重试；UA-10／11、A15／A17／A20。 |
| 北京时间周期与 UTC 日窗口 | 边界、时区、未完结时段明确，概览与明细一致；混合周期不称全站本月量。 | 固定时刻测试；UA-08、A24。 |
| 归档、重叠异常与分页 | 当前／归档分开；不假加异常总数；总数非页长，可进入同范围列表。 | 非空夹具与页面；UA-03／07／08。 |
| 历史缺日／采样时间缺失 | 不把补齐零当真实历史，不画伪趋势，读取时间不冒充源采样时间。 | 固定源响应；UA-07／08／18。 |
| 人工开通但收款未核实 | 次数和条款准确，实收未核实而非标价或零；多币种、部分退款、余额退款分开。 | 订单／凭据样例；经营规则独立验收。 |
| 出口到期仍绑定或仅内部核验 | 未确认停用和回收不计为可交付空闲；内部测试不称公网固定独享。 | 绑定、操作及核验证据；UA-15。 |
| 用户与管理员真实任务 | 各自找对对象及动作，正确解释状态和证据，关键误判修正后复测。 | 任务记录与可访问性；UA-19，经营任务单列。 |

### 只读对账

隔离开发数据库使用 `REPEATABLE READ READ ONLY` 事务、明确超时和时区，结束 `ROLLBACK`。固定对象、筛选、分页、版本，在原记录、真实 DAL 聚合、API、页面与明细之间核对。原始对象先分别计数再关联，避免多对多膨胀。本地结果不代表生产规模或线下收入。

多个 HTTP 请求不是同一数据库快照；记录时间与变化，需要逐字核对时用稳定夹具。自然增长不误判为错误，任意容差也不能掩盖丢量。金额按币种、实际发生时间及凭据精确金额核对，不能直接沿用旧支付的跨币种浮点汇总。

**GET 不保证只读：** 当前 `/api/services/{id}/subscription` 会记录用量并提交事务，Node 部分统计读取含 `reset:true`。纯只读审计排除这些路径，先检查实际副作用；订阅导入仅放在明确范围的隔离功能测试中。

### 网络质量与吞吐

优先复用现有原生客户端／节点测试。记录探测位置与接入网络、受控目标、服务／Node 标识、核心版本、真实代理协议与路由、DNS／IP 版本、时段、截止时间、计划／实际样本数、失败阶段及载荷。验证代理停用时没有直连回退，不访问客户内容。

轻量体验抽样可从管理员位置和一处代表性接入网络，在两个明确时段各取 30 次小请求；这是可调整的实验参数，不是 SLA。分位置／协议／目标报告成功、失败与耗时，不混池。单次成功不证明所有目标、平台、时段和持续容量；单次失败不能独自定位责任。

参考 [RFC 2681](https://www.rfc-editor.org/rfc/rfc2681)、[RFC 7679](https://www.rfc-editor.org/rfc/rfc7679)、[RFC 7680](https://www.rfc-editor.org/rfc/rfc7680) 明确 IPPM 包类型、端点、时限和时钟误差。HTTP 总耗时不叫 IP RTT，HTTP 请求失败率不叫 IP 丢包率，未同步时钟不声称精确单向时延。

仅在确需判断持续吞吐时，参考 [RFC 6349](https://www.rfc-editor.org/rfc/rfc6349) 在隔离资源测试，记录 MTU、RTT、窗口、重传、连接数、两端资源与接收端有效字节。标准建议测量长于 30 秒，不提供本产品合格线。[iperf3](https://software.es.net/iperf/invoking.html) 必须证明穿过目标代理；TCP 默认不限速，限速按每条并发流计算。预先约束时长、并发、速率、方向和字节预算；影响非测试业务即停止。限速测试不证明最大容量，按 [RFC 6815](https://www.rfc-editor.org/rfc/rfc6815) 不在生产网套用 RFC 2544 过载基准。

### 可访问性与证据包

受影响流程参考 [WCAG 2.2](https://www.w3.org/TR/2024/REC-WCAG22-20241212/)：语义关系／不只靠颜色（1.3.1／1.4.1）；普通文字 4.5:1、大字 3:1、必要非文本 3:1（1.4.3／1.4.11）；320 CSS px 重排与表格合理例外（1.4.10）；键盘无陷阱、焦点可见且不被完全遮挡（2.1.1／2.1.2／2.4.7／2.4.11）；目标 24×24 CSS px 或规范例外（2.5.8）；错误说明与辅助技术状态消息（3.3.1／3.3.2／4.1.2／4.1.3）。局部验收不宣称全站 AA 符合性。

证据包至少包含版本／源码摘要、环境／时区、脱敏原始记录、执行命令、输入与预期、实际结果、时间、截图／日志、清理、失败基线及未覆盖项。“事实—聚合—展示—动作—结果”任一环节无法解释都保留缺口，不由整体测试通过掩盖。

## 6. 仅需业务确认的经营问题

1. **收退款依据与关联：** 用哪些现有凭据、谁核实；一笔款覆盖多服务、分次付款、预收及退款如何分配和关联？
2. **经营目的与成本：** 先看现金收支还是收入／利润；后者由谁确定确认时点、报告币种／汇率、成本范围、账期及分摊？
3. **状态与退款完成：** 免费／赠送、未收、待收、未知如何区分；现金退回和余额退回各以什么证据认定完成？

字段、倍率、缓存、窗口、路径和采样能力由实施者自行核查，不交给用户猜测。长期故障、通知和服务质量承诺保持原指南待定边界；本方案未引入这些行为，不将其变成本轮前置问题。

## 7. 实践中的调整机制

遇到接口语义与假设不一致、样本不完整、实际成本超预期、组件限制、用户误解或更小且完整的路径时，随时重新评估。可以缩小一次改动、改变顺序、替换验证方法，或暂不展示证据不足的指标，不必等整批失败。

| 变化 | 处理方式 |
| --- | --- |
| 措辞、排列、组件复用、拆分、测试方法等，不改业务语义和验收目标 | 在已有授权内调整，记录理由／影响，补足验证；不反复要求无意义确认。 |
| 新采集／存储、额外成本、新页面或基础设施、自动通知／探测、权益或经营规则变化 | 暂停依赖决定的部分，说明证据、成本、风险和选项；用户明确决定后更新需求／指南，继续无依赖工作。 |
| 旧验收结论越界或发现失败 | 保留原始记录，在实施计划追加勘误、范围和补验要求，不静默重写历史或删除失败基线。 |
| 上游版本／环境变化 | 重核受影响字段和行为，旧结论只适用于原范围，不自动继承。 |

实质调整统一记录在实施计划：**日期 → 问题及证据 → 原假设 → 决定与理由 → 范围／成本 → 保持的约束 → 新验收方法 → 结果与遗留项**。业务决定注明来源；文字微调不堆过程日志。

稳定方法改变同步本文，业务规则改变同步需求／指南，进度和实测证据只有实施计划一份。调整始终保留独立服务、权限、计量、真实表达和隐私边界。产品实现、本地验证、真实环境验证与发布分别登记，不以计划调整跳过必要门禁。
