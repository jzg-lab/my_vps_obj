# 合作伙伴计划

本文属于[上游兼容参考](../upstream/index.md)，说明单层伙伴归因及资金义务。本项目一期不开放该营销销售流程；管理员人工开通 `UserService` 不等于外部付款，也不应据此生成佣金。

下文入口和配置属于上游兼容机制，不能靠开启设置绕过本项目的[运行时边界](../upstream/index.md#运行时边界)。项目进度与验收范围只查[本轮本地最终验收](../implementation-plan.md#本轮本地最终验收)。

合作伙伴计划是独立于普通推荐的单层获客渠道。获批伙伴获得独立 Telegram／网页链接，其客户符合条件的成功外部付款会产生佣金，余额按币种分别核算。提现由人工处理：伙伴申请，管理员核对收款信息并登记结果。

上游功能默认关闭，不追溯发放佣金。以下首次开启、密钥轮换与回滚步骤仅供已明确采用该兼容功能的部署维护；不是本项目接手时的默认操作清单。

后台伙伴列表分页加载，余额、提现预留、客户数和佣金由整页四次 SQL 聚合取得，不逐行查询。排序只聚合所选指标，币种、退款、冻结期和取消提现规则与详情一致。提现申请与伙伴／入驻申请同时开始加载。

<a id="безопасное-первое-включение"></a>

## 安全首次开启

1. 备份，并将 backend、worker、frontend 更新到同一版本，暂不开启计划。
2. 用 `openssl rand -base64 32 | tr '+/' '-_'` 生成密钥，设置 `PARTNER_REQUISITES_ENCRYPTION_KEY` 和唯一 `PARTNER_REQUISITES_KEY_ID`，重建 backend、worker。
3. 进入“设置 → 营销计划 → 合作伙伴计划”，确认加密诊断正常。
4. 设置币种、排除销售类型、费率、冻结期和至少一种提现方式。银行卡必须有 `card_number`，快速支付系统必须有 `phone`，加密货币必须有 `address` 且至少一种网络。
5. 保持计划关闭，运行核对报告：

   ```bash
   docker compose exec -T backend python -m scripts.partner_reconciliation
   ```

6. 开启计划、批准测试伙伴，完成两次外部付款和一次完整提现。确认 worker 正常后，再单独开启余额支付。

<a id="где-находятся-разделы-и-как-применяется-включение"></a>

## 入口与配置生效

- 用户 Mini App 只在 `PARTNER_PROGRAM_ENABLED` 开启时显示“合作伙伴”。关闭时 `/partner` 返回首页。批准前显示申请表或状态；`active` 伙伴可查看链接、客户、佣金、分币种余额和提现。
- 后台“合作伙伴”在关闭计划后仍可用，以便处理旧提现和历史。提醒数每 30 秒更新，统计待审核入驻与未完成提现。
- “设置 → 营销计划 → 合作伙伴计划”保存数据库覆盖项，运行中后端无需重启。同一管理员会话立即重读公开 Mini App 数据，入口随之显示／隐藏；其他会话下次加载数据时更新。
- `PARTNER_AUTO_ENROLLMENT_ENABLED` 开启免申请模式。确认后同时开启计划，后端在设置事务中为所有未封禁已有用户创建 `active` 资料；新用户在首次机器人／网页流程获得资料，不显示申请表，费率取加入时默认值。
- 自动加入保持幂等：不重复创建活跃资料，不恢复暂停／关闭资料，不覆盖个别费率。获得活跃资料的待审申请转为 `approved`，不批量发通知；拒绝记录保留。封禁用户不加入，解封后可通过正常用户流程获得资料。关闭自动加入只停止未来加入，不影响已有资料、链接、余额和义务。
- `PARTNER_REFERRAL_PROGRAM_DISABLED` 默认关闭。与计划同时开启时，无伙伴资料用户仍可普通推荐，伙伴则禁止普通推荐操作。Mini App 保留灰色推荐卡片并叠加说明，激活码字段仍可用；Telegram 隐藏推荐按钮，旧回调和内联请求返回说明。
- 收款加密密钥与 ID 只放环境变量，变更需重启；已有收款信息需按后文轮换。

<a id="заявки-ссылки-и-атрибуция"></a>

## 申请、链接与归因

人工模式中，用户在“合作伙伴”申请，同一时刻最多一条 `pending`；同文案网络重试返回原申请。管理员可带个别费率批准、附消息拒绝、后续允许重申、暂停资料、调整费率或手工创建。自动加入模式拒绝多余的新申请，概览先幂等创建活跃资料。

新申请通知 `LOG_CHAT_ID`／`LOG_THREAD_ID`。批准、拒绝及资料状态 `active`、`paused`、`closed` 变化向用户发送本地化 Telegram 通知；批准和直接创建另写日志群。同一待审申请的 HTTP 重试不重复通知。

伙伴链接使用独立代码，不使用普通推荐载荷。首次接触归因只为新用户创建；第二条链接、自邀、暂停资料或已有账号不会更换客户归属。仅邀请注册接受有效伙伴链接，普通推荐关系仍独立。

禁止普通推荐时，活跃伙伴旧普通推荐链接仍可用，新注册会通过当前伙伴资料建立与专属链接相同的伙伴首次归因。伙伴获得金钱佣金，客户奖励天数取决于 `PARTNER_CLIENT_WELCOME_BONUS_ENABLED`、`PARTNER_CLIENT_PAYMENT_BONUS_ENABLED`、`PARTNER_ONE_BONUS_PER_CLIENT`，不向邀请者发普通天数。暂停／关闭伙伴链接不创建任何推荐或伙伴归因；没有伙伴资料的普通链接行为不变。

切换不追溯改写 `referred_by_id`、已发奖励或旧伙伴归因。禁止开启后，沿旧普通关系付款不再给伙伴或客户发普通天数；独立活跃伙伴归因仍可按客户付款奖励及其首购限制发放客户部分。金钱佣金不受普通推荐禁用影响。已有账号打开链接不重新归属。关闭整个伙伴计划后，此限制失效，普通推荐恢复。

管理员可轮换链接代码，旧链接停止建立新归因，已有客户和财务历史不变。伙伴可成为另一伙伴的直接客户，但计划只有一层，不向上级传递其客户佣金。

两个默认关闭的独立客户奖励：

- `PARTNER_CLIENT_WELCOME_BONUS_ENABLED`：只给开关已启用时，通过活跃伙伴 Telegram／网页链接新注册的用户一次欢迎奖励。金额对应的时长和套餐取普通推荐欢迎奖励设置。注册时固定权利，不追溯旧客户；后绑定 Telegram 可领取既有权利。共用已领取标记及任意历史订阅检查，防止重复领取或叠加普通／伙伴欢迎奖励。
- `PARTNER_CLIENT_PAYMENT_BONUS_ENABLED`：只给已归属客户发放其按时长套餐矩阵中的被邀请者奖励，伙伴不获邀请者天数。`PARTNER_ONE_BONUS_PER_CLIENT` 独立决定仅首个成功付款或每次成功付款发放，默认仅首购。重复 webhook 不重复发放，同客户并发付款在检查历史和保存奖励前通过用户锁串行化。

客户奖励不追溯。首购限制针对历史首个成功付款，不是首次实际发奖励：归因前付款、开关关闭时付款、矩阵未配置奖励的周期，也会使后续付款不再是首购。需要奖励每次未来合适付款时，关闭首购限制。

已有普通 `referred_by_id` 且邀请者仍可普通推荐时，普通关系优先，不叠加伙伴天数。该优先级只影响双方奖励天数，金钱佣金仍由独立伙伴归因决定。因此导入普通推荐后，伙伴可获佣金；未禁用普通推荐时，天数按普通规则计算。禁用后，任意伙伴资料（包括暂停／关闭）都停止普通奖励；暂停／关闭伙伴或关闭计划也阻止新伙伴客户奖励。导入和人工归因不产生欢迎奖励，未来付款只在无普通 `referred_by_id` 且满足首购限制时发客户矩阵部分。

普通推荐关闭时，后台提供批量将已有 `referred_by_id` 转为伙伴客户归因。预览显示伙伴数、已有关系、可导入客户、已导入项、冲突及历史付款数。执行前管理员需单独确认：历史付款不重算，佣金权利从导入时开始。

操作幂等，不重复绑定。同伙伴关系视为已导入；属于其他伙伴或自邀视为冲突，不重新归属。每个新增客户的伙伴创建审计事件。普通推荐开启时，预览和执行都拒绝，避免两种机制同时改历史。

<a id="комиссии-и-баланс"></a>

## 佣金与余额

归属客户每次成功付款只生成一次决定，保存激活码后的实际扣款、币种及精度、费率、渠道和销售类型。伙伴余额内部支付、不支持币种、排除销售类型标为 `excluded`，不创建收入记录。

金额用整数最小单位、费率用基点保存，按 `HALF_UP` 舍入。资金调整与已入账退款使用独立账本记录，不直接改写历史金额；账本状态并非完全不可变。冻结期结束时，兼容 worker 将佣金从 `pending` 转为 `posted`；冻结前退款可将其标为 `void`，冻结后退款追加负数冲正。具体状态转换见 [`partner_commission_service.py`](../../backend/bot/services/partner_commission_service.py)。余额可为负，偿清前禁止新提现和余额支付。

管理员增加、扣除、设置余额都创建独立账本、原因及审计事件。报表不能在未明确换汇时累加不同币种。

<a id="вывод-средств"></a>

## 提现

伙伴选择方式、金额或“最大”，附幂等键提交。服务器锁定资料后重新检查最低额、币种、网络、活跃申请数和可用余额，创建时立即预留。伙伴只能取消 `requested`。管理员可将 `requested` 转为 `processing`／`rejected`／`failed`；`processing` 转为 `paid`／`rejected`／`failed`。`failed` 不自动返还预留，管理员可重试处理或拒绝返还。只有 `canceled`／`rejected` 释放预留，且只释放一次。

新提现通知同一管理日志群，包含安全用户资料、金额、币种、内部编号，不包含完整收款信息。状态进入处理中、已付、拒绝、失败、取消时通知用户；失败明确说明金额仍预留。创建或状态幂等重试不重复通知。

提现方式、币种精度、网络和收款掩码在申请时保存快照，后续修改／停用方式只影响新申请，不阻止已有申请完成。

完整收款信息用 AES-GCM 加密，并绑定伙伴与幂等键。用户、列表、事件只包含掩码。管理员只能在已打开详情中揭示，每次揭示写审计。达到 `PARTNER_REQUISITES_RETENTION_DAYS` 后，worker 删除已完成申请密文，保留掩码和财务历史。

<a id="оплата-из-баланса"></a>

## 使用余额付款

个人／伙伴余额自动续费在“系统 → 设置 → 支付系统 → 余额”配置，双方设置互有链接。`USER_BALANCE_RECURRING_ENABLED` 默认关闭。结账开启自动续费时，所选周期及弹性限额必须全部由伙伴余额支付；后续只使用同来源，检查可用性和冻结期，不用个人余额或外部渠道补差。见[从所选余额自动续费](user-balance.md#автопродление-с-выбранного-баланса)。

活跃伙伴可用余额购买时长、流量包、设备或付费切换套餐。余额在激活码之后使用，不足时外部渠道支付剩余，且不低于渠道最低额。余额覆盖完整服务器报价时，不创建外部账单，直接内部完成。Telegram Stars 和渠道控制价格的方式不与余额混用。

付款与扣账在同一事务创建，账本键绑定 `payment_id`。取消、过期、创建／激活失败或退款时，补偿入账只返还一次，worker 重试遗漏返还。返还后收到迟到成功 webhook，将补偿入账标为 `void`，原扣款重新生效，避免重复资金；后续退款可再次激活同条补偿。全内部购买不增加现金收入；混合付款只将真实外部支付余款计入外部收入。

<a id="ежедневная-сверка-и-диагностика"></a>

## 每日核对与排障

只读报告不修改数据，也不输出个人资料：

```bash
docker compose exec -T backend python -m scripts.partner_reconciliation
```

`ok` 应为 `true`。`issues` 检查成功付款缺失决定、佣金／提现账本不一致、重复业务引用、空幂等键及已删除实体引用。`balance_rows` 只从已入账记录重算；`negative_balances` 单独显示冲正后的允许欠款，负余额本身不会使报告失败。

worker 每分钟幂等执行：

- 补齐缺失决定与冲正。
- 释放冻结期结束佣金。
- 释放卡住的内部消费，包括扣款后激活前中断的全额余额结账。
- 返还终态结账的伙伴余额预留。
- 应用审计与收款信息保留期限。

先修复差异原因，再使用常规核对、冲正或人工调整，不直接编辑账本。

<a id="ротация-ключа-реквизитов"></a>

## 收款密钥轮换

轮换在同一事务解密全部仍保留的信息，再以新密钥加密。成功前不要替换 `.env` 当前密钥。

1. 停止新提现、停止 backend 和 worker，备份数据库。
2. 保留旧 `PARTNER_REQUISITES_ENCRYPTION_KEY`、`PARTNER_REQUISITES_KEY_ID`，临时增加 `PARTNER_REQUISITES_NEW_ENCRYPTION_KEY`、`PARTNER_REQUISITES_NEW_KEY_ID`。
3. 试运行，逐行检查可解密性，不写入：

   ```bash
   docker compose run --rm backend python -m scripts.rotate_partner_requisites_key
   ```

4. 使用 `APPLY=1` 重复。所有行同一事务修改，审计只记录密钥 ID 和行数：

   ```bash
   docker compose run --rm -e APPLY=1 backend python -m scripts.rotate_partner_requisites_key
   ```

5. 成功后才把新密钥／ID 移至主要变量，删除临时 `PARTNER_REQUISITES_NEW_*`，启动进程并检查一条测试申请揭示。

试运行或应用失败时保留旧密钥，事务不提交。成功后回滚需反向轮换或恢复备份；按恢复策略保管旧密钥，不放仓库。

<a id="rollback-и-приватность"></a>

## 回滚与隐私

功能回滚时关闭计划、新提现和余额支付。不回滚只追加迁移、不删表，后台历史必须继续支持已有欠款与付款。上游伙伴核对使用共享 worker；本项目是否调度该任务另见[运行时边界](../upstream/index.md#运行时边界)。处理完伙伴待办不意味着可以停止整个 worker，应同时核对服务交付、计量、通知等任务的运行要求。

普通 PostgreSQL 备份包含全部伙伴表，必须同时保留匹配版本密钥，否则无法恢复收款信息。删除账号会关闭并匿名化资料、申请、归因，但保留匿名账本与义务。客户与伙伴只看到公开快照标签，不看到邮箱、Telegram ID、渠道付款 ID 或订阅数据。开启前需发布适用地区的条款、税务／身份核验要求和隐私告知；Core 只提供技术机制，不自动保证法律合规。
