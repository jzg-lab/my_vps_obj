# 赠送订阅

本文属于[上游兼容参考](../upstream/index.md)，保留礼品购买、领取、退款及历史处理规则。本项目一期不开放礼品购买和在线支付；管理员人工开通独立服务也不等于创建礼品。

下文礼品基于[上游单订阅套餐](subscriptions.md)，不代表可以为 `ServicePlan` 自动生成独立服务。所述按钮、默认开关和接口用于兼容维护，受本项目[运行时边界](../upstream/index.md#运行时边界)约束；实际交付范围只查[本轮本地最终验收](../implementation-plan.md#本轮本地最终验收)。

购买者在“奖励 → 我的礼品 → 赠送”选择订阅。付款后获得链接，由其他用户自行激活。期限从激活时开始计算，未激活礼品没有失效期限。

启用礼品或推荐计划时，首次打开应用会显示“奖励”标签。购买可用性通过 `/me` 的 `settings.gifts_enabled` 返回，不依赖礼品列表加载。关闭购买后，已付款礼品和保存的链接仍可访问。“我的礼品”使用共享卡片组件及奖励页面间距。

<a id="покупка-и-оплата"></a>

## 购买与付款

- 可购买已发布的按时长套餐、周期和弹性设备／普通流量／premium 流量限额。不出售无期限流量包或单独设备续费礼品。
- 可使用激活码。折扣影响付款金额，奖励天数和流量发给接收者；代码使用记录关联购买者及付款。
- 支持可用的单次支付、个人余额、合作伙伴余额，也可按常规结账使用外部支付补差。Tribute 和由渠道管理的循环订阅不适用于礼品；礼品不开启自动续费。
- 礼品购买不改变购买者订阅；同一付款重复 webhook 不重复创建礼品。
- 付款确认前显示等待状态及返回付款按钮。发放成功后显示链接，并保存在“我的礼品”。

群发可通过“应用页面 → 奖励”按钮或 `{gifts_link}` 跳转礼品购买页面；该链接不指向具体礼品。首页不显示购买横幅。

<a id="получение-и-активация"></a>

## 领取与激活

1. 接收者打开链接，登录已有账号或注册。应用在浏览器中保存待领取礼品直到登录完成，多条链接按队列保存。仅允许邀请注册时，有效未使用的礼品链接可代替单独邀请链接。服务器验证礼品，但不建立推荐关系；已使用、已撤销或未付款的礼品不能用于注册。
2. 在礼品对话框中核对套餐、期限、限额和激活账号，明确确认后才激活。打开链接本身不会激活。
3. 激活成功后不能再次转赠。同一接收者重复请求返回原结果，不重复增加期限。

链接是秘密凭据：首位确认激活者获得礼品。投递邮箱不限制接收账号；购买者不能领取自己尚未使用的礼品。换设备、清空浏览器数据或无法使用本地存储时，应重新打开原链接。

现有订阅条件兼容时，礼品延长有效期。套餐不同、权益组成变化或开启自动续费时会阻止激活；需等当前订阅结束或关闭自动续费，礼品仍保留。试用按礼品下单时保存的 `TRIAL_DAYS_STRATEGY` 处理：`add_remaining` 保留剩余试用时长，`start_from_payment` 从礼品激活时开始付费期限。

Remnawave 暂时不可用时，礼品以“激活中”状态绑定接收者，其他账号不能领取。worker 自动重试，接收者也可再次尝试。操作完成前，不应让其他付费订阅变更与其竞争。

激活成功后，网页应用重新加载账号数据，关闭礼品窗口并打开首页，无需手动刷新即可看到有效订阅。

<a id="реферальное-начисление"></a>

## 推荐奖励

“按推荐计划计入礼品激活”（`REFERRAL_GIFT_ACTIVATION_ENABLED`）位于推荐计划规则中，默认开启。推荐计划和此设置都开启时，成功激活按照接收者已有邀请关系增加期限。礼品链接不创建或更改邀请关系；购买或打开链接不发放奖励。激活不产生合作伙伴客户付款奖励或合作伙伴佣金。

双方的奖励与时长取自礼品下单时保存的条件。隐藏、删除或更改套餐不影响这些条件。`REFERRAL_ONE_BONUS_PER_REFEREE=true` 时，共享一次首个有效事件：个人成功购买，或启用此选项后的礼品激活。后续购买和礼品不再向双方增加期限。为 `false` 时，每个成功激活礼品都可奖励，但各只计一次。

开启设置不会追溯计算旧激活。关闭时的激活不占用首次事件；已计入的激活在关闭后仍占用首次事件。注册欢迎奖励单独计算。

激活成功时保存双方待发放权益，由常规奖励 worker 交付；面板故障与重复激活请求不会重复发放。迁移 `0104_gift_referral_qualification` 增加激活计入标记和权益来源，不会把旧礼品标为已计入。

<a id="сохранение-условий"></a>

## 保存购买条件

创建付款时保存套餐、时长、价格、所选限额和激活码条件。套餐修改、隐藏或删除不会替换已付款条件。激活后，订阅保存套餐快照，用于权限发放及后台限额／节点组同步；后续常规购买或切换套餐可用新订单条件替代。

快照不会重建已删除的 Remnawave 对象。管理员在面板删除相关节点组或服务器后，需恢复相应资源可用性。未激活礼品仍保存在数据库中，不因目录缺失而消失。

<a id="email-и-уведомления"></a>

## 邮件与通知

配置 SMTP 和 `SUBSCRIPTION_MINI_APP_URL` 后，购买者可选择向指定邮箱投递礼品。worker 在确认付款后发送；失败最多重试五次，间隔至少五分钟，购买者和管理员可查看状态。投递失败不会取消礼品，购买者仍可复制链接自行发送。如果 SMTP 接受邮件后进程中断，可能重复投递包含同一链接的邮件。

可用 Telegram 的购买者会收到链接消息。配置的管理日志群收到带礼品标记和付款编号的购买通知。独立日志事件为 `gift_purchased`、`gift_activated`、`gift_email_delivery`，记录标识及结果，不在购买或投递管理日志中保存秘密链接。

<a id="администрирование-и-эксплуатация"></a>

## 管理与运维

- “礼品 → 创建礼品”由管理员免费发放。可选择已发布套餐、期限及弹性限额；配置邮件后可填写接收邮箱。不需要付款、激活码或扣余额。套餐、期限与限额按付费礼品方式保存，后续修改／隐藏套餐不改变已发放礼品。
- 管理员成为创建者与所有者。链接在创建后立即可见，已授权管理员也可从礼品详情再次查看。后台不公开购买者礼品链接，总列表不包含秘密链接。
- 免费发放记录为金额 `0`、渠道 `admin_gift`、来源 `admin_grant` 的成功操作，不计入现金收入、外部付款数量或客单价。财务统计单独统计累计免费发放／激活数，排除已取消发放。免费发放不产生合作伙伴佣金或推荐奖励。
- 创建记录为 `gift_created_by_admin`，包含操作者与操作 ID，并通过常规成功事件发送管理 Telegram 日志。同一 `request_id` 重试返回同一礼品，即使套餐已隐藏，也不会再次发放或产生重复事件。邮件使用现有投递队列，邮件不可用不影响管理员获取链接。
- 管理发放不依赖 `GIFTS_ENABLED`，该开关只控制用户购买；已创建礼品仍可领取。
- “设置 → 通用 → 赠送订阅”的 `GIFTS_ENABLED` 默认 `True`，控制新购买。关闭不阻止已有付款完成、历史查看、邮件投递和已付款礼品激活；与 `REFERRAL_PROGRAM_ENABLED` 独立。
- “礼品”显示购买者、接收者、套餐、金额、渠道、日期与状态，支持搜索、状态／来源筛选、排序、每页 25 条，手机端显示卡片。图标按钮打开礼品与用户详情。
- 详情显示保存的权益、奖励、折扣、个人与合作伙伴余额扣款、付款和邮件投递结果。用户历史显示最近 100 次购买，管理员可查看完整历史。
- 管理员只能撤销已付款且处于 `ready` 的礼品。操作锁定付款与礼品，不与开始激活竞争；`activating`、`activated` 不可撤销。默认按实际支付总价（`checkout_total_amount`，缺失时使用 `amount`）以单次幂等 `gift_refund` 账本记录全额退回购买者个人余额。退款保存管理员和原因，默认要求填写原因，兼容 API 的例外见下文。退款覆盖混合支付全部金额，即使余额功能关闭仍入账，资金保留至后续开启。
- 邮件投递和未完成激活恢复需要运行 `worker`。升级时先由常规 `migrate` 服务应用 `0077_subscription_gifts`、`0078_gift_entitlements`。

购买使用现有结账接口，传入 `gift: true` 和可选 `gift_recipient_email`。已登录接口：`GET /api/gifts/options`、`GET /api/gifts`、`POST /api/gifts/preview`、`POST /api/gifts/claim`；管理列表为 `GET /api/admin/gifts`。准确契约见 [OpenAPI](../api/index.md)。

管理发放：`GET /api/admin/gifts/options`、`POST /api/admin/gifts`，字段为 `request_id`、`plan_id`，以及可选 `checkout_addons`、`recipient_email`。这里的 `plan_id` 是上游销售选项标识，不是数据库 `ServicePlan.id`。详情为 `GET /api/admin/gifts/{gift_id}`。撤销接口 `POST /api/admin/gifts/{gift_id}/revoke` 接受 `reason`、`without_reason`、`restore_promo_usage`、`refund_to_balance`。默认要求原因去除首尾空白后至少三个字符；兼容 API 的 `without_reason=true` 允许空原因。所有管理接口校验管理员权限，客户端不能指定退款金额或资金来源。

项目余额流程必须先在同一事务内将未使用已付礼品的实付金额记入购买者余额，再撤销权益。上游 [`revoke_paid_gift`](../../backend/bot/services/gift_revoke.py) 仍接受 `refund_to_balance=false`，这说明存在兼容分支，不是本项目允许丢弃已付礼品且不退款的业务规则。后续余额工作必须核对退款与撤销的原子性、幂等及回归，不能只恢复旧按钮；参见[贡献入口约束](../../AGENTS.md)和[用户余额](user-balance.md#礼品撤销与退款)。
