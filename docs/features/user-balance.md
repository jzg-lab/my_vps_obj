# 用户余额

本文属于[上游兼容参考](../upstream/index.md)，说明保留的钱包、账本和资金核对能力。本项目一期不开放在线支付及余额购买流程，人工开通独立服务不扣取本页余额。

下文充值与付款接入[上游单订阅结账](subscriptions.md)，不代表 `ServicePlan`／`UserService` 已具备余额支付。配置开关、关闭后的存量处理与财务义务需分别理解；项目实现及验收范围只查[本轮本地最终验收](../implementation-plan.md#本轮本地最终验收)。

用户余额是 Minishop 可选的内部钱包。上游用户可通过常规支付渠道充值，再全额或部分支付订阅、续费、流量和设备加购。资金操作保留账本记录，不是反复覆盖用户表中的单一余额字段；金额历史与记录状态应分开理解，补偿记录可在 `posted` 与 `void` 之间按付款结果转换。

普通余额和合作伙伴余额是不同资金来源。普通余额不可提现。管理员可在两者之间转换，但从普通余额转入的合作伙伴资金仍不可提现，不会把用户充值变成可提取的合作伙伴收入。

<a id="включение-и-настройка"></a>

## 开启与配置

在上游兼容界面进入“系统 → 设置 → 支付系统 → 余额”。以下设置作为覆盖项优先于 `.env`，但不绕过本项目的[运行时边界](../upstream/index.md#运行时边界)：

| 变量 | 用途 |
| --- | --- |
| `USER_BALANCE_ENABLED` | 在个人中心显示余额并允许充值，默认关闭。关闭后保留已有余款的一次性支付能力，但禁止从个人余额自动续费。 |
| `USER_BALANCE_RECURRING_ENABLED` | 允许从所选个人／合作伙伴余额自动续费，默认关闭。使用合作伙伴资金不要求同时开启个人余额。 |
| `USER_BALANCE_CURRENCY` | 余额币种代码；留空时继承 `DEFAULT_CURRENCY_SYMBOL`。 |
| `USER_BALANCE_TOPUP_MIN_AMOUNT` | 用户单次最低充值金额。 |
| `USER_BALANCE_TOPUP_MAX_AMOUNT` | 用户单次最高充值金额，不得低于最低金额。 |
| `USER_BALANCE_TOPUP_PRESETS` | 快捷金额 JSON 数组，如 `[500, 1000, 2000, 5000]`；超出范围的值会被剔除。 |

币种代码转为大写，已知币种按真实精度处理，例如 RUB／USD／EUR 为两位小数，无小数币种按整数处理。界面优先显示本地化货币符号，未知时显示币种代码。

API 金额必须是符合币种精度的正有限 JSON 数值。布尔值、数字字符串及多余小数位会被拒绝。JSON 数值 `1e2` 与 `100` 相同，服务器允许；Mini App 输入框只接受以点或逗号作小数分隔符的普通十进制写法，并提示格式错误。

更改 `USER_BALANCE_CURRENCY` 不会自动换算旧账本。历史保留原币种，界面和新操作使用当前币种。已创建充值的迟到回调仍按原账单币种入账，避免设置变化使已付款资金丢失。切换币种前仍建议处理完未结付款，并单独确定旧余额迁移方式。

<a id="пользовательский-сценарий-пополнения"></a>

## 用户充值流程

1. 用户在首页或个人中心设置中点击充值。
2. 输入金额或选择预设金额。
3. 选择可用外部支付渠道。
4. Minishop 创建 `sale_mode=balance_topup` 的常规 `Payment`。
5. 验证回调成功后，金额只入账一次，可用于购买；不会激活或延长订阅。

充值方式不包含 Telegram Stars、普通余额和合作伙伴余额，避免循环转账及资金混用。支付渠道还必须支持所选币种与金额。创建付款前执行请求限流。

重复回调保持安全：最终处理时锁定付款，已完成付款不重复处理，充值账本使用 `user-balance-payment-topup:<payment_id>` 作为键。充值成功后，“系统 → 日志”记录用户、金额、币种、渠道及付款 ID；后端技术日志也记录这些主要字段。启用 `LOG_PAYMENTS` 和 `LOG_CHAT_ID` 后，在事务成功提交后向 Telegram 支付话题／群发送独立的“用户余额已充值”通知，包含相同信息，不包含虚构订阅周期，重复回调不重复通知。

成功充值发生退款或冲正时，创建独立负数账本记录，不修改原记录。如果资金已经消费，余额可能变为负数；偿清欠款前，阻止新的扣款及要求可用余额的人工操作。

<a id="оплата-из-баланса"></a>

## 使用余额付款

用户在结账时启用余额支付。普通与合作伙伴余额都可用时，默认选择普通余额，可通过下拉菜单切换来源。

- 所选余额足够支付完整服务器报价时，创建内部成功 `Payment` 用于审计，再执行常规购买收尾，无需外部渠道。
- 部分支付时，向外部渠道提交剩余金额，同时保存完整价格及所选余额预留金额。
- 外部渠道存在最低金额时，限制余额使用量，确保剩余支付不低于最低值。
- 结账币种必须与所选余额一致。
- 创建付款时，在事务中锁定用户与余额，避免并发重复消费。
- 外部付款取消、过期或失败时，以独立账本记录返还预留。迟到回调随后确认成功时，返还记录标为无效，原扣款继续生效。
- 对全额余额购买，后台核对会在收尾进程异常中断后返还卡住的预留，并重新检查缺少返还记录的终态付款。

合作伙伴余额的冻结期、负数冲正与支付可用性，见[合作伙伴计划](partner-program.md#оплата-из-баланса)。

<a id="автопродление-с-выбранного-баланса"></a>

### 从所选余额自动续费

启用 `USER_BALANCE_RECURRING_ENABLED` 后，独立余额支付卡片显示自动续费开关。仅订阅可用，且单一所选来源必须覆盖完整服务器报价，包括弹性流量与设备限额。混合支付、礼品和单独资源加购不会创建循环订阅。余额不会加入通用支付渠道列表或按钮。

付款成功后保存来源（`user_balance` 或 `partner_balance`）、周期和所选限额。订阅到期前，worker 按常规自动续费流程，从该来源扣除全额；不会用另一余额或外部渠道补差。余额不足则不扣款、不续费，用户可先充值。每次扣款都会重新检查来源可用性及币种。

自动续费开启时不能单独加购流量或设备，用户可在个人中心关闭。余额渠道和合作伙伴设置提供互相跳转入口；合作伙伴余额能否用于付款仍由合作伙伴设置控制。

<a id="администрирование"></a>

## 管理操作

功能开启时，用户详情主要信息及用户列表独立列显示普通余额。合作伙伴计划启用时，旁边以普通余额币种显示合作伙伴余款。列表对当前页批量聚合余额，不逐用户查询。

用户详情的余额管理支持：

- 增加、扣除或设置普通余额为指定金额。
- 填写操作流程要求的原因／备注；字段在技术上允许留空，留空会记录默认原因。
- 为活跃合作伙伴在普通与合作伙伴余额之间转换。
- 点击“最大”填入所选来源的全部可用余款。
- 查看保留金额与来源的账本记录及其当前状态。

扣款、转换不得超过当前余额。前端校验用于便利，服务器仍在锁定用户与合作伙伴资料后执行最终校验。幂等键保护重复提交。

转换还有以下规则：

- 必须存在活跃合作伙伴资料，暂停／关闭状态不适用。
- 两侧均使用 `USER_BALANCE_CURRENCY`，单次操作不能混合币种。
- 合作伙伴转普通余额时，先消耗不可提现部分，再消耗可提现部分。
- 普通转合作伙伴余额时，创建不可提现记录。
- 两条账本记录在同一事务中创建，不允许部分转换。

## 礼品撤销与退款

未使用已付礼品的退款与普通充值退款是不同操作。项目规则要求先将礼品实付金额记入购买者个人余额，再撤销礼品权益，二者处于同一事务；余额功能关闭也不能丢弃这笔资金。金额采用保存的完整结账总价，缺失时回退付款金额，不能只退混合支付中的外部部分。

兼容实现使用 `gift_refund` 账本种类及 `user-balance-gift-refund:<gift_id>` 幂等键。上游 API 还保留跳过退款选项，不应把它当作本项目允许的默认删除路径。具体条件、接口与源码依据见[礼品管理](gifts.md#администрирование-и-эксплуатация)；后续余额改动须同时核对退款路径和回归，不通过删除礼品或账本绕过资金义务。

<a id="отключение-и-эксплуатация"></a>

## 关闭与运维

关闭功能会隐藏普通余额，禁止用户新充值及个人余额自动续费，但保留已有余款的一次性支付、历史和资金。管理员仍可查看用户账本，为重新开启做准备。不要手动删除账本或直接用 SQL 改余额，应提交附带原因的调整。

排查问题时对照：

1. `Payment` 的 `sale_mode`、状态、金额、币种、渠道。
2. `reference_type=payment`、`reference_id=<payment_id>` 的余额账本记录。
3. 管理日志中的 `balance_topup_succeeded`。
4. 后端回调和支付渠道技术日志。

渠道显示付款成功但余额未到账时，先检查 `user-balance-payment-topup:<payment_id>`，再决定是否人工处理。迟到重试叠加人工入账会造成重复充值。
